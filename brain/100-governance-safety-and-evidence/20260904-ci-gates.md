# CI Gates & Exact-Subject Evidence

Source: agent-platform#CI-GATES.md

## Overview

`tools/ci/run_gates.py` is the **first executable evidence boundary** for the repository. It runs deterministic commands only after the checked-out Git commit matches the expected event subject, then writes a JSON receipt.

## Core Principle

**Subject Validation First**: Every gate verifies checked-out commit matches expected event subject BEFORE running any tests.

**Deterministic Only**: Gates execute deterministic commands only; no external network calls, no stochastic tests.

## Receipt Contents

Gate receipt contains:

- **Tested commit**: Exact Git SHA
- **Tree**: Exact tree object SHA
- **Commands**: List of gates executed
- **Exit codes**: Result of each gate
- **Output digests**: SHA-256 of each command's output

**Portable**: Receipt is portable JSON, can be verified without network access.

## Scope Binding

### Pull Request Receipts

- Bind to GitHub's checked-out **merge subject**
- Subject is PR head SHA merged into PR base
- Receipt proves exact merge-commit state

### Main Branch Receipts

- Bind to **accepted integration commit**
- Subject is main branch HEAD at test time
- Receipt proves accepted state entered CI

### Failed Subject Handling

A failed or stale subject:
- Returns **nonzero exit code**
- Still uploads receipt
- Documents failure reason

## Non-Goals (Not Yet Proven)

This slice proves:
- Execution of exact-subject tests
- Exact-subject evidence binding
- Deterministic gate repeatability

This slice does **NOT** yet prove:
- Separate cryptographic CI principal
- Automatic promotion authority
- Complete delivery lifecycle proof

**Rule**: Promotion must remain **disabled** until controller validates:
1. Trusted workflow/run identity
2. Receipt validity
3. Independent review completion
4. Expected integration head

## Local Reproduction

Run the same gates locally with:

```bash
python3 tools/ci/run_gates.py \
  --receipt /tmp/agent-platform-ci-receipt.json \
  --expected-subject "$(git rev-parse HEAD)" \
  --gate-json '{"name":"governing-policy","argv":["python3","tests/docs/test_governing_policy.py"]}' \
  --gate-json '{"name":"identity-helper","argv":["python3","tests/identity/test_configure_git_identity.py"]}' \
  --gate-json '{"name":"identity-range","argv":["python3","tests/identity/test_validate_commit_range.py"]}' \
  --gate-json '{"name":"ci-runner-tests","argv":["python3","tests/ci/test_run_gates.py"]}'
```

### Reproducibility Rules

- **Same inputs** (exact subject, gates, codebase) produce **identical output digests**
- **Receipt is portable**: Can move between machines, runs, time periods
- **No path in receipt**: Repository paths, executable paths, local config excluded
- **External attestation needed**: Controller/CI runner provides argv, executables, digests separately

## Gate Categories

### Governing Policy Gate

Verifies operating model and decision framework are intact.

**Command**: `python3 tests/docs/test_governing_policy.py`

**Exit 0**: Policy document intact, no stale claims

**Exit 1**: Policy drift detected

### Identity Helper Gate

Verifies commit identity configuration works correctly.

**Command**: `python3 tests/identity/test_configure_git_identity.py`

**Exit 0**: Identity helper functions correctly

**Exit 1**: Identity configuration broken

**Exit 2**: Invalid identity inputs

### Identity Range Gate

Verifies commit trailers in candidate range are correct.

**Command**: `python3 tests/identity/test_validate_commit_range.py`

**Exit 0**: All commits have correct Agent-Actor and Agent-Run-ID trailers

**Exit 1**: Trailer mismatch or missing trailers

**Exit 2**: Git objects not found or range invalid

### CI Runner Tests

Verifies gate runner itself functions correctly.

**Command**: `python3 tests/ci/test_run_gates.py`

**Exit 0**: Gate runner works

**Exit 1**: Gate logic broken

## Workflow Integration

### GitHub Actions Workflow

- Runs on every pull request
- Runs on every main branch commit
- Uploads receipt as artifact
- Records exact workflow run ID, attempt, job name, conclusion

### Binding to Delivery Pipeline

Gates integrate with delivery pipeline:

1. **Implementer phase**: Produces candidate commit
2. **CI gates** (this gate): Validates exact commit
3. **Review phase**: Reviews against exact commit SHA
4. **Promotion phase**: Promotes only if gates passed and review approved

**Rule** (DFL-016): Poll with bounded timeout, distinguish `no checks` from failure, revalidate head before acceptance.

## Exit Codes

| Code | Meaning |
|------|---------|
| `0` | All gates passed; tested commit is valid |
| `1` | Gate logic failed; tested commit is invalid |
| `2` | Input validation failed (stale subject, missing gates, etc.) |

## Falsifiers (Tests)

How to verify CI gates are actually being enforced:

1. **Commit tampering**: Modify committed code; gate should fail
2. **Identity mismatch**: Change Agent-Actor trailer; identity gate should fail
3. **Missing receipt**: Remove artifact; next gate should error
4. **Subject mismatch**: Run gates on different commit; should fail with stale-subject error
5. **Subprocess escape**: Try to inject command in gate args; should reject with input validation

## Limitations

- **Not cryptographic CI principal**: CI does not mint its own authority
- **Not automatic promotion**: Requires explicit controller validation + review approval
- **Receipt is evidence, not authority**: Receipt proves tests ran; controller decides if passing is enough
- **No network isolation**: Gates can run if network is unavailable, but cannot verify network state

## Next Steps (Not Built Yet)

To enable automatic promotion:
1. Controller must validate trusted CI workflow identity
2. Controller must fetch and validate receipt
3. Review must complete on exact same commit SHA
4. Promoter must verify receipt + review before advancing

Until those controls exist, promotion must remain manual or gated by external approval.

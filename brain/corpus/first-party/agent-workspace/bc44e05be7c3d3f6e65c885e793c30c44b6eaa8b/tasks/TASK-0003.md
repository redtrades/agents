Diagnosis so far (full detail in the GitHub issue, not repeated here):

Mike's repro — `HTTP 400: All routed providers rejected the request as
invalid (stopped early: retry time budget 45s exceeded...)` — traced through
`~/.hermes/logs/errors.log` and `freeapi.db`'s `requests`/`request_attempts`
tables to a five-step chain: (1) Hermes oneshot calls attach a 700KB-1.3MB
skill/tool loadout, (2) something in that payload trips the gateway's
denylist, which since the 2026-08-24 403-removal change silently reroutes
even a `X-Sensitivity: public`-labeled request into `notrain` instead of
403ing, (3) the `notrain` pool is still bloated to ~26 platforms
(unfixed, `project_freellmapi_profile_drift_2026_08_24` memory), so the
reroute can land on Mistral/NVIDIA/OVH, (4) those reject the large request
with a bare 400 whose real reason is lost to a genuine bug in vendored
`freellmapi` v0.8.3 (`upstreamErrorText()`,
`server/src/providers/openai-compat.ts:109` — only reads
`error.message`/`detail`/`title`, falls back to generic `res.statusText`
otherwise), and (5) the 45s `FALLBACK_TIME_BUDGET_MS` is shorter than the
60s per-provider timeout actually observed in the DB, so the chain gives up
after 1-2 slow hops.

Both prime suspects going in — the global `model.thinking_budget: 400` in
`~/.hermes/config.yaml` and the 2026-08-24 provider-alias pass — were
checked and ruled out; neither reaches this code path (detail in the
GitHub issue).

Not yet done: getting the actual raw Mistral/NVIDIA/OVH rejection body to
confirm the exact offending field needs either restarting the live
FreeLLMAPI server (`server/dist/index.js`, PID 22710 observed) after a
patch, or reading the platform API key out of `freeapi.db` to repro
directly — the first is a live-service restart other sessions depend on,
the second was blocked by this session's own credential-access guard. Both
need Mike's sign-off before proceeding, per `~/CLAUDE.md` rule 2 (no
destructive/irreversible change — including restarting a shared service —
without explicit approval) and the credential-handling boundary. Pruning
the `notrain` pool drift is also Mike's call per the existing memory entry,
not something to do unilaterally even though it's implicated here.

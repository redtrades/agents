# Critique of the fable proposal

2026-08-21. The fable proposal was asked "how do I build this" and answered that question well. It was not asked "is this a business," and mostly didn't try to be one — which is the actual gap Mike's request was pointing at. This is a critique of that proposal specifically, evaluated against the three source documents (business plan, financial model, market-snapshot template) it was responding to.

## Keep

- **Deterministic pipeline over agent frameworks.** The reasoning (CrewAI's ~3x token overhead vs LangGraph, reliability compounding badly across chained agents, "add complexity when something specific breaks") is sound and directly applicable — this is a nightly batch job with the same five steps every night, not an open-ended agent task. Nothing about the business case changes this.
- **Never self-host USASpending's data.** Correct and well-evidenced — the official stack is genuinely team-scale infrastructure (Docker, Django, Elasticsearch, full DB snapshot restores) for a problem the hosted API already solves for free.
- **Reuse of existing federal-contracting MCP servers for interactive R&D**, not production. Reasonable, low-risk, doesn't affect the customer-facing product.
- **Provenance-first generation (source `award_id` required on every claim).** This is correctly identified as more than an anti-hallucination guardrail — it's a sellable accuracy claim GovWin can't easily match, because GovWin's product is analyst-curated, not machine-cited. Treat this as a marketing asset, not just an engineering discipline.
- **The relevance-dataset framing.** Correctly identifies that "what actually matters to SDVOSBs, filtered over time" is the durable moat, not the data itself (which is free and public). This matches the business plan's own moat ranking (§8) and should stay the top-ranked defensibility argument.
- **Golden-set evals in CI.** Cheap, appropriate discipline for a pipeline whose output quality directly gates the review-time bottleneck (below).

## Change

- **Billing route.** The proposal's open question #3 floats a Claude Max subscription as a live, cheaper alternative to the pay-per-token API, on the premise that Claude plans now include separate Agent SDK credits that don't touch interactive limits. Verified against Anthropic's own support docs: that feature was announced for June 15, 2026 and **paused the same day** — it does not currently exist. Separately, Anthropic's Consumer Terms of Service bar automated, resale-adjacent use of subscription credentials regardless of the credit-pool question, and Anthropic tightened enforcement of exactly this in April 2026. **This isn't a live tradeoff — it's a closed question.** Use the pay-per-token API under Commercial Terms, full stop. (The business plan document itself already assumed this — "Claude API with model orchestration" — so the correction is to the proposal's open question, not to the underlying plan.)
- **The USASpending "50K row cap."** Couldn't independently verify that specific number; the real, verified constraint is a ~10K-record pagination ceiling on the search endpoint, with the same fix (use the async bulk-download endpoint for nightly deltas, not paginated search). Doesn't change the architecture, just the citation.
- **SAM.gov treated as interchangeable with USASpending.** The proposal lists them as equally safe, redundant data sources ("Multiple redundant sources (USASpending, FPDS, SAM); alert on pipeline breaks" — risk mitigation table). They are not equally safe: USASpending is CC0/public-domain, unambiguously clear for commercial resale. SAM.gov's Terms of Use explicitly bar commercial resale of D&B-sourced entity data, and the general "not for commercial purposes not covered by this Agreement" clause is broad and unscoped for ordinary API-key users. This is a real business-model risk the proposal doesn't surface at all — it appears only in the risk table as "API changes," which is the wrong risk. Fix: source entity/recipient identity primarily from USASpending's own award records; use SAM.gov narrowly for opportunity notices; get the Data Use Agreement's scope confirmed by counsel before launch, not after.

## Drop

- **The training-data argument for GitHub PRs as the review interface.** The proposal frames "PRs give free training-data capture" as a reason to accept the mobile friction. This is a false tradeoff: capturing before/after edit diffs as training signal is a database-logging decision, not a Git decision — a custom review web page can log the same edit deltas into Postgres just as easily as a PR merge does. The actual tradeoff is: PR review adds per-customer navigation overhead (finding the right open PR among N every week) that a purpose-built single-queue review UI removes, and review time is this business's hard ceiling on customer count (see the improved business idea for the math). Since the review UI isn't on the pipeline's critical path — Ingest/Detect/Synthesize can ship and prove the data pipeline in weeks 1–4 regardless of which review UI ships in week 5 — the "one extra week of build" cost the open question poses is not a real tradeoff against the thing that actually gates revenue. Build the simple web page. GitHub Mobile's file editor is more capable than a knee-jerk "PRs don't work on phones" assumption (it can edit a single markdown file in-app since 2022) — but that's beside the point once the training-data justification is removed; there's no remaining reason to route the business's core weekly bottleneck through a code-review tool built for reviewing diffs, not approving customer deliverables.
- **Treating the customer ceiling as solved.** The proposal's KPI dashboard sets "founder review time per week: ceiling 60 min" as a target, and the business plan states review as a flat "30–45 min weekly" figure at every subscriber count from 3 to 63. Neither document models review time as a function of subscriber count, and there's no way a fixed weekly number holds from 3 customers to 63 — each customer gets an individually personalized draft that needs individual judgment. This is the single largest gap between "an architecture" and "a business," and it's addressed in the improved business idea document, not fixed here — flagging it as something to drop from the current framing (a fixed constant) rather than carry forward unquestioned.

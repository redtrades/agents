## 1. Diagnosis — What's Weak, Missing, or Risky

### 1.1 Run Inspection: No CLI, Manual File Crawling Only

**Current state:** Runs live in `runs/<run_id>/` with `trace.json` and `GATE-REPORT.json` per run. The runner has a `--review <RUN_ID>` flag (`factory/runner.py:147-204`) that prints a one-screen scorecard, but:
- It only reads `trace.json` and `assemble/data.json` — does **not** surface `GATE-REPORT.json` details (per-stage gate breakdown, fail lines)
- It does not show envelope outputs, stage timing, or gate latency
- No way to query a single stage's envelope or gate results
- No JSON output for programmatic consumption
- No filtering by stage, gate, or status

**Risk:** Operators must `cat runs/.../trace.json | jq` or open files manually. No standard "what happened in this run?" workflow.

### 1.2 Run Comparison: Does Not Exist

**Current state:** Zero tooling. To compare two runs, operator manually diffs `trace.json` files or `GATE-REPORT.json` files.

**Missing:**
- Compare gate pass/fail across runs
- Compare envelope outputs (what changed in `match/tiered_firms.json`?)
- Compare timing (which stage regressed?)
- Compare notice selection (same solicitation? different firms?)

**Risk:** Regression detection is manual. "Did the matcher change behavior?" requires forensic work.

### 1.3 Manual Gate Override / Approval: Does Not Exist

**Current state:** Gates are **fail-closed** (`factory/runner.py:275-288`, `factory/gates/registry.py:482-493`). Any gate failure halts the pipeline immediately. No mechanism to:
- Override a specific gate failure with human approval
- Mark a gate as "waived with reason" and continue
- Record override audit trail (who, when, why, which gate)

**Risk:** Transient external API failures (SAM.gov, USASpending) block the entire pipeline. No "Mike approved this known-acceptable deviation" path.

### 1.4 Run Replay / Rerun: Full Re-run Only

**Current state:** Re-running means `python -m factory.runner factory/pipelines/govcon-sources-sought-packet.yaml --run-id <new_id>`. This re-executes **all 9 stages** from scratch.

**Missing:**
- `--resume-from <stage>` flag to start at a failed stage
- `--rerun-failed-only` to re-execute only stages that failed gates
- Preserve prior successful stage outputs (envelopes, data files) instead of recomputing

**Risk:** Debugging a `package` stage failure (gate: value) requires re-running ingest→normalize→triage→match→extract→assemble→gate→synthesize (~minutes) just to re-test the package stage.

### 1.5 Partial Re-run from Failed Stage: Does Not Exist

**Current state:** `factory/runner.py` has no `resume_from_stage` parameter. The `prior` dict is built incrementally during the run (`factory/runner.py:219, 292`). No persistence of "completed stages" to enable resume.

**What would be needed:**
- Record completed stage envelopes/outputs in trace DB (already done via `envelope_outputs` table)
- CLI flag to load prior successful stages from a previous run_id
- Stage modules must be idempotent (safe to re-run with same inputs)

**Risk:** Long pipelines waste compute and operator time on known-good stages.

### 1.6 Notification / Alerting on Gate Failure: Does Not Exist

**Current state:** Gate failures print to stdout (`factory/runner.py:276-281`) and return exit code 1. No:
- Webhook/Slack/email notification
- PagerDuty / OpsGenie integration
- Structured event emission (JSONL, CloudEvents)
- Run-level alerting (e.g., "3 consecutive runs failed at `match` gate: freshness")

**Risk:** Silent failures in cron/scheduled runs. Operator discovers failure only by checking logs manually.

### 1.7 Run Retention / Cleanup: Does Not Exist

**Current state:** `runs/` directory accumulates indefinitely. Current count: 20+ run directories (see `ls runs/` output). No:
- TTL policy (e.g., keep last 50 runs, or runs < 30 days)
- Size-based cleanup (keep < 5 GB)
- Archive-to-cold-storage before delete
- Protected runs (tagged "keep", "production", "gold-set")

**Risk:** Disk pressure, noisy `ls runs/`, no compliance with data retention policies.

### 1.8 CLI Ergonomics: `factory review run-id` Exists But Limited

**Current state:** `python -m factory.runner --review <RUN_ID>` (`factory/runner.py:147-204`) prints a scorecard. Gaps:
- No `factory` entrypoint (must run as module)
- No subcommands: `factory runs list`, `factory runs show <id>`, `factory runs compare <id1> <id2>`, `factory runs purge --older-than 30d`
- Output is human-only (no `--json`, `--csv`)
- Does not show `GATE-REPORT.json` per-stage breakdown

**Risk:** High cognitive load to remember invocation pattern. Not scriptable.

### 1.9 Run Dashboard: Does Not Exist

**Current state:** No web UI, no TUI, no Grafana/Graphite/Prometheus exporter.

**What operators need:**
- List recent runs with status (green/red), duration, notice ID, NAICS
- Drill into run → stage → gate → fail lines
- Time-series: gate pass rate, stage duration, run duration
- Filter by pipeline, date range, status

**Risk:** No operational visibility. "How many packets did we produce this week?" = manual count.

### 1.10 Multi-Run Comparison: Does Not Exist

**Current state:** No tooling to compare N runs side-by-side.

**Use cases:**
- Compare gold-set runs (precision/recall tracking)
- Compare same notice across different pipeline configs
- Trend analysis: gate latency, matcher output stability, packet quality score


**Gate report changes:**
```json

  "passed": false,
  "lines": [...],
  "fails": [...],

    "reason": "SAM.gov transient 500, Mike approved 2026-08-25",

    "approved_at": "2026-08-25T14:30:00Z"
  }
}
```

**Runner logic:** If gate fails but override exists for that stage.gate, treat as passed (with audit line).

### P0: Partial Re-run / Resume from Stage (High Impact, Medium Effort)

**Files to modify:**
- `factory/runner.py` — add `--resume-from <stage>` and `--resume-from-run <run_id>` flags
- `factory/stages/*.py` — ensure idempotency (stages should be safe to re-run with same inputs)

**Design:**
```bash
# Resume from failed stage using prior run's successful outputs
factory run pipeline.yaml --resume-from package --resume-from-run 20260825T031705Z-d0a76c

# Rerun only failed stages from a prior run
factory run pipeline.yaml --rerun-failed --resume-from-run 20260825T031705Z-d0a76c
```

**Implementation:**
1. Load prior run's `trace.json` → identify completed stages with `status: "ok"`
2. Copy those stages' `envelope.json` and output files to new run directory
3. Populate `prior` dict from copied envelopes before starting pipeline
4. Skip stages already in `prior` (or re-run only if `--rerun-failed`)

**Idempotency check:** Each stage must produce identical outputs given identical inputs. Verify by hash-comparing outputs on resume.

## 4. Risks / Dependencies

### 4.1 Stage Idempotency (Blocks Partial Re-run)
- Stages must be pure functions: same inputs → same outputs
- Current stages use `now_iso()` in envelopes (`factory/util.py`) — timestamps will differ on re-run
- **Fix:** Make timestamps deterministic (use `ctx.today` or run start time) or exclude from hash comparison
- External API calls (SAM.gov, USASpending) must be cached or mocked for true idempotency

### 4.2 Override Audit Trail Integrity
- Override records must be tamper-evident (append-only, signed, or in git)
- **Risk:** Operator overrides gate, forgets to document, audit fails
- **Mitigation:** Require `--approver` flag, write to `run_dir/overrides.json`, include in `GATE-REPORT.json`

### 4.3 Notification Spam
- Failed runs in cron will fire alerts every run
- **Fix:** Deduplication (alert on first failure, then on state change: failed→ok, failed→different gate)
- Add `--quiet` / `--notify-on-change-only` flags

### 4.4 Retention Policy Data Loss
- Accidental purge of gold-set runs
- **Fix:** `protect_tags` in config, `--dry-run` default, confirmation prompt, tagging CLI

### 4.5 Dashboard Data Freshness
- Static HTML requires rebuild on every run
- **Fix:** Integrate into runner: `export_trace_json()` → also call `dashboard.update_run(run_id)`
- Or run dashboard build as post-step in pipeline

### 4.6 Comparison Across Pipeline Versions
- Comparing runs from different pipeline YAMLs (e.g., V5 vs V6) may be apples-to-oranges
- **Fix:** Record pipeline spec hash/version in trace, warn on cross-version compare
